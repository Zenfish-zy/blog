# 📚 Git 核心命令与分支管理学习笔记

## 一、 指针移动的核心：`checkout` 与 `reset`

Git 的许多操作本质上都是在“移动指针”。理解这两个命令，就理解了 Git 的定位导航系统。

- **`git checkout`**：**移动 `HEAD` 指针**。
  - **作用**：切换你当前工作区看到的视图。它可以指向一个分支，也可以直接指向某个具体的提交（进入 Detached HEAD 状态）。
- **`git reset`**：**移动“分支标签”（并带着 `HEAD` 一起移动）**。
  - **作用**：改变当前分支的历史轨迹。

## 二、 深度解析 `git reset` 的三种模式

`reset` 操作会影响 Git 的三个区域（工作区、暂存区、本地仓库）。

| **模式**             | **分支指针（本地仓库）** | **暂存区 (Index)**       | **工作区 (Working Directory)** | **典型应用场景**                                             |
| -------------------- | ------------------------ | ------------------------ | ------------------------------ | ------------------------------------------------------------ |
| **`--soft`**         | ✅ 移动到目标节点         | ❌ 保持原样               | ❌ 保持原样                     | 撤销了 commit，但保留了之前 add 的内容。                     |
| **`--mixed`** (默认) | ✅ 移动到目标节点         | ✅ **恢复为目标节点状态** | ❌ 保持原样                     | 撤销 commit 和 add。常用于**将多个细碎的 commit 压缩成一次干净的提交**。 |
| **`--hard`**         | ✅ 移动到目标节点         | ✅ **恢复为目标节点状态** | ✅ **恢复为目标节点状态**       | 彻底抛弃当前的所有修改，回到某个历史状态。**⚠️ 高危操作：未 commit 的改动会丢失！** |

## 三、 安全的后悔药：`git revert`

- **核心机制**：“向前滚”。它不改变、不抹除过去的任何历史记录，而是生成一个新的、内容与目标提交完全相反的**“反向操作”提交**。
- **应用场景**：在多人协作的**公共分支**上撤销代码。它极其安全，不会导致同事本地仓库的历史轨迹产生冲突。

## 四、 分支整合：`merge` 与 `rebase` (重点与易错区)

这两个命令是团队协作中最常用的分支合并方式，但它们的底层逻辑和表现形式截然不同。

### 1. `git merge` (合并)

- **核心机制**：尊重历史。把目标分支的改动和当前分支融合，生成一个新的“合并提交”（Merge Commit）。

- **指针移动**：当前所在的分支标签移动到最新的 Merge Commit，**被合并的分支标签留在原地不动**。

- **示例图解**：

  在 `main` 上执行 `git merge bugfix`：

  ```Plaintext
  # 合并前：
        A---B---C (main)
             \
              D---E (bugfix)
  
  # 合并后：创建节点F，main移到F，bugfix留在E！
        A---B---C-------F (main)
             \         /
              D-------E (bugfix) 
  ```

### 2. `git rebase` (变基)

- **核心机制**：改写历史。将当前分支上独有的提交“摘”下来，然后在目标分支的最新节点上，依次重新“播放”（Cherry-pick），生成全新的提交节点（Commit Hash 改变），从而保持提交历史为一条完美的直线。

- **底层原理解密 (你的高光时刻总结)**：

  在 `bugfix` 上执行 `git rebase main`，Git 在后台做了三件事：

  1. 找到 `bugfix` 独有的提交 (D, E) 复制为副本。
  2. 把这些副本接到 `main` 后面生成新节点 (D', E')。
  3. **核心动作：执行 `git reset`，将 `bugfix` 的标签强行移动到最新的 `E'` 节点上。** (`main` 标签留在原地不动)。

- **示例图解**：

  ```Plaintext
  # 变基后：bugfix 跟着新节点走了，main 还在原地！
                    D'---E' (bugfix) 
                   /
        A---B---C (main) 
             \
              D---E (旧节点变成没有标签指向的孤儿，会被回收)
  ```

  *(注：变基后，通常需要切换回 main 分支执行 `git merge bugfix` 进行快进合并，让 main 也指向 E')*

- **⚠️ 铁律**：**绝对不要在已经推送到远程、有其他人正在使用的公共分支上使用 `git rebase`。**

## 🚫 常见误解排雷区 (Misconceptions)

- **❌ 误解 1：`git merge` 或 `git rebase` 结束后，被合并/变基的源分支（如 bugfix）会被自动销毁。**
  - **✅ 真相**：**Git 底层从来不会自动销毁任何分支标签。** 我们在 PR/MR 完成后看到分支消失，是因为托管平台（如 GitHub/GitLab）的自动化设置，或者是开发者手动执行了 `git branch -d bugfix`。合并和变基只负责处理 Commit 和移动标签，不负责清理标签。
- **❌ 误解 2：执行变基 (`git rebase main`) 时，是把当前分支的提交拼接到 main 上，然后把 main 的标签移到最后。**
  - **✅ 真相**：完全弄反了。变基操作的始终是**当前分支**。它是在 main 的基础上重写当前分支的历史，最终被强行移动（reset）的是**当前分支（bugfix）的标签**，而 main 的标签在整个 rebase 过程中纹丝不动。
