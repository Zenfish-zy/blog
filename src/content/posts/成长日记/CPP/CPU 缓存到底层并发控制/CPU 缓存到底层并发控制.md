# 核心学习笔记：从 CPU 缓存到底层并发控制

## 一、 CPU 核心架构与指令执行基础

CPU 的核心设计哲学是 **“极致的速度”**。为了避免被缓慢的主内存拖后腿，CPU 内部有着严格的分工与层级：

- **三大核心组件：**

  - **控制器（Control Unit）：** 负责流程控制与指令解码。包含程序计数器（PC，指向下一条指令的地址）和指令寄存器（IR，存放当前正在执行的指令）。
  - **运算器（ALU）：** 负责所有的算术与逻辑运算。
  - **寄存器（Register）：** CPU 内部的“私有工作台”，速度极快（0 周期）。**所有数据必须从缓存加载到寄存器中，才能进行运算。**

- **指令周期：** 取指（从缓存/内存读取） -> 译码（控制器判断指令类型） -> 执行（ALU 读取寄存器进行计算） -> 写回（将结果写回寄存器或缓存）。

## 二、 缓存（Cache）的读写策略

现代 CPU 引入了 L1/L2/L3 多级缓存。当 CPU 修改数据时，如何保证缓存和主内存的数据同步？有两种经典策略：

### 1. 写直达（Write-Through）

- **机制：** 每次修改数据，既写缓存，也直接穿透写入主内存。
- **特点：** 数据绝对安全同步，但频繁的内存 I/O 会严重拖慢 CPU 执行速度，现代 CPU 极少单纯使用此策略。

### 2. 写回（Write-Back）—— 现代 CPU 的绝对主流

- **机制：** 只要数据在缓存中命中，所有的覆写 **只在缓存中进行**，绝对不和内存通信。
- **脏位（Dirty Bit）：** 当缓存中的数据被修改，与主内存不一致时，该缓存行会被标记为“脏（Dirty = 1）”。
- **触发写回内存的时机（关键）：**
  1. **内部触发（缓存替换）：** 发生 Cache Miss，需要腾出这块缓存空间给新数据时。如果旧数据是脏的，必须先写回主存。
  2. **外部触发（总线嗅探）：** 多核环境下，如果核心 1 捏着脏数据，核心 2 突然通过总线请求读取该数据的物理地址，核心 1 必须中止对方请求，将脏数据交出（写回内存或直接跨核心转发）。

## 三、 多核缓存一致性：MESI 协议与状态机

在多核环境下，必须保证所有核心看到的数据是一致的。这依赖于硬件层面的 **总线机制** 和 **MESI 协议（一种有限状态机）**。

CPU 读写缓存的最小物理单位是 **Cache Line（缓存行，通常为 64 字节）**。

### MESI 四大状态

- **M (Modified - 已修改)：** 脏数据 + 当前核心独占。代表数据被改过，且最新数据只在我这里。
- **E (Exclusive - 独占)：** 干净数据 + 当前核心独占。数据和主内存一致，且只有我有。
- **S (Shared - 共享)：** 干净数据 + 多核共享。数据和主内存一致，多个核心可以 **同时极速并发读取**，互不干扰。
- **I (Invalidated - 已失效)：** 废弃数据。该缓存行已被其他核心宣告作废，不可读写。

### 并发写入的规则（写传播与写串行化）

如果核心 1 想修改一个状态为 S（共享）的数据：

1. **竞争总线：** 它必须先通过硬件仲裁获得总线控制权（写串行化）。
2. **广播失效：** 向总线发送信号，要求其他所有拥有该数据的核心将缓存状态改为 I（已失效）。
3. **独占修改：** 核心 1 将自己的状态改为 M，并在本地缓存中完成修改。

*注：现代 CPU（如 Intel 的 MESIF 或 AMD 的 MOESI）优化了 M 状态数据的传递。当其他核心想读 M 状态数据时，不再需要缓慢地写回主内存，而是直接通过 CPU 内部总线进行* *“缓存到缓存的直接传输（Cache-to-Cache Transfer）”* *。*

## 四、 性能杀手：伪共享（False Sharing）

因为 MESI 协议是按 **64 字节的 Cache Line** 为单位管理的，这就带来了一个极其隐蔽的性能 Bug。

- **场景：** 核心 1 频繁修改变量 A，核心 2 频繁修改变量 B。两者逻辑独立，毫无交集。
- **灾难发生：** 如果 A 和 B 在物理内存中紧挨着，它们会被打包进 **同一个 Cache Line**。
- **缓存乒乓（Cache Ping-Pong）：** 核心 1 修改 A 时，会导致核心 2 包含 B 的整个缓存行失效；核心 2 修改 B 时，又会导致核心 1 连带 A 一起失效。两个核心疯狂互相让对方的缓存失效，导致极速的缓存退化成缓慢的内存交互，并发性能断崖式下跌。

------

## 五、 并发 Bug 的万恶之源：寄存器与缓存的鸿沟

即使有强大的 MESI 协议，在高级语言中执行 `i = i + 1` 依然会产生并发 Bug（最终结果变小）。这是因为：**MESI 只能管缓存，管不到 CPU 的私有寄存器！**

- **读写权限的硬件逻辑：**
  - 硬件极其欢迎 **并发读**（S 状态），因为性能极高。
  - 硬件严格限制 **并发写**（独占 M 状态），必须排队且让别人失效。
- **漏洞还原（读-改-写 操作）：**
  1. **Load (读)：** 核心 1 和 2 瞬间同时将缓存中的 `i=0` 读进各自脱离了 MESI 管控的私有寄存器。
  2. **Add (算)：** 各自在寄存器内算出 `1`。
  3. **Store (写)：** 核心 1 抢到总线，将 `1` 写入缓存（触发 MESI 让核心 2 缓存失效）。核心 2 随后获得总线，但它 **依然使用自己寄存器里的旧数据算出的 `1`** 强行覆写缓存。两次加法，结果只加了 1。

------

## 六、 终极解法：锁（Lock）与原子操作

为了填补“并发读不受限”导致的寄存器脏读漏洞，必须引入软件层面的 **锁** 或硬件层面的 **原子指令**。

- **纠正核心误区：** 锁并不是在物理硬件层面上给数据贴封条限制读取。
- **锁的本质：** 保护一段 **临界区（Critical Section）** 代码的执行流。
  - 它将 `Load -> Add -> Store` 这三个独立的指令，强行打包成一个 **不可分割的整体（原子操作）**。
  - 在核心 1 彻底完成“读、算、写”这整套动作并释放锁之前，直接把核心 2 挡在第一步的 `Load` 指令之外。
- **核心目的：** 阻止其他核心在不恰当的时机，提前把即将过期的旧数据“偷看”进私有寄存器。
